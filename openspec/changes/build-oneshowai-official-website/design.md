## Context

OneShowAI 当前缺少统一的官方对外入口，需要一套轻量、可扩展、移动端友好的品牌网站。项目约束为：
- 单仓内交付（本地项目目录）
- 首阶段不引入后台、登录、支付、CMS 等复杂系统
- 后续要保留拓展空间（博客、CMS、产品后台、在线体验、多语言）

## Goals / Non-Goals

**Goals:**
- 交付可发布的 5 页官网（Home/About/Products/Projects/Technology/Contact）
- 建立统一视觉与信息架构，清晰表达品牌与能力
- 支持移动端、桌面端，具备基础 SEO 与性能优化基础项
- 保持页面结构可扩展，便于后续接入博客与产品体验

**Non-Goals:**
- 不开发用户系统、支付系统与 CMS
- 不实现真实数据后台（先以静态内容为主）
- 不接入用户登录/鉴权体系

## Decisions

- **技术方案：** 使用纯 HTML/CSS/JS 的静态站实现。
  - **原因：** 当前阶段需求以展示为主，最小化复杂度；便于快速上线与后续迁移。
  - **备选：** 选用 React/Vue 框架。
    - 放弃原因：引入构建链路和运行时开销增加，短周期内不划算。

- **样式策略：** 使用统一变量与组件化命名（hero、card、section）构建页面样式。
  - **原因：** 可快速扩展新页面且降低重复代码。
  - **备选：** 使用独立页面样式。
    - 放弃原因：会导致后续新增页面维护成本增大。

- **内容组织：** 采用“页面 + 全局组件（导航/页脚）”模式。
  - **原因：** 满足 MVP 且保留后续新增页面能力。
  - **备选：** 单页长列表设计。
    - 放弃原因：页面拓展时不利于信息分层与 SEO。

## Risks / Trade-offs

- **[Risk] 内容未最终齐备 →** 在开发中使用占位文本，发布前需完成真实内容替换。
  - **Mitigation:** 每个页面保留可追溯数据字段块，待内容确认后替换。
- **[Risk] 设计风格与实际品牌不一致 →** 初稿偏工程导向导致审美偏差。
  - **Mitigation:** 后续以“设计复核”作为一个固定更新节奏，必要时迭代 CSS tokens.
- **[Risk] 首屏加载图片与视觉素材缺失 →** 使用占位图导致专业感不足。
  - **Mitigation:** 预留真实图/视频位，优先接入高质量素材。

## Migration Plan

1. 本变更上线前：补全真实文案、Logo 与合作方图标。
2. 发布第一版后：若需托管于 CDN/静态托管，直接上传构建目录。
3. 回滚策略：若线上发布异常，保留上一个稳定版本页面文件，快速替换静态资源即可恢复。
